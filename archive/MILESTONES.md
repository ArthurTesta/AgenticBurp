# Next major milestones

Ordered by value-at-risk, not by size. The two "process" milestones (M1, M2) come first because everything else in this project has been verified against mocks, stubs, or unit tests — never against the thing it's actually for. That's not a criticism of the work done; it's the single largest source of uncertainty this project currently carries, and it's cheaper to resolve now than after more features are built on top of an unverified foundation.

## M1 — Run the whole thing against a real, running Juice Shop instance, end to end — **done, see `LIVE_TARGET_VERIFICATION_REPORT.md`**

This was previously (incorrectly) classified as structurally impossible in this sandbox. It wasn't — it required actually running the setup recipe already documented in `HANDOVER.md`, not new infrastructure. Once running, this surfaced three real, previously-undiscovered bugs that had made every one of the 36 specialist agents completely non-functional (a system-prompt validation false positive) and would have rejected nearly all real HTTP traffic even once that was fixed (a broken shell-injection pattern). All three fixed and regression-tested. One thing this milestone's original framing got right: a real Ollama backend is still not available in this sandbox (network policy), so the loop was verified up to — and including — a clean, correct failure at that boundary, not all the way through a completed LLM analysis. That remains the one genuine environmental limit.

**Why this is first.** Every claim in this codebase's own history is qualified as "unit-tested," "mock-tested," or "compile-verified." Grep the handovers: "no Juice Shop instance was rebuilt," "never run against a live target," "sqlmap's actual binary was never invoked." The Python side's core loop (dispatch → agent → critique → validator → chain → report) has *never* been exercised as a whole against a real, imperfect, noisy target in this project's current combined-branch state. Unit tests prove each piece is internally consistent; they cannot prove the pieces compose correctly under real traffic, real timing, real HTTP edge cases (chunked encoding, redirects, malformed JSON, non-UTF8 bodies) that a hand-constructed test fixture won't reproduce.

**What "done" looks like:** stand up Juice Shop, drive traffic through Burp (or a lightweight substitute capture harness if Burp itself isn't available in the target environment), run a full `analyze()` pass on a representative sample of exchanges, and — critically — **manually verify a sample of the findings against the target's actual known vulnerabilities** (Juice Shop ships a scoreboard of intended vulnerabilities; use it as ground truth). This produces the project's first real precision/recall numbers instead of unit-test pass counts, which measure something different.

**What this would surface that unit tests structurally can't:** false-positive rate in practice, whether the fast-path/coordinator dispatch logic actually selects sensible agents on real traffic shapes, whether the critique pass's rejection rate is sane (rejecting too much = wasted agent work; too little = the adversarial review isn't doing anything), and whether `sqlmap.py`'s safety-gate integration behaves correctly against a real sqlmap binary rather than a constructed fake path.

## M2 — The forced-egress safety proxy — **done, see `CHANGELOG_AUDIT_FOLLOWUP.md` and `PROXY_SETUP.md`**

Already fully designed in `PROXY_WATCHER_TODO.md` — this is a "build it," not a "figure it out" milestone. It closes the specific, named structural gap `safety_gate.py` cannot close on its own: process boundaries (sqlmap's subprocess), runtime boundaries (the JVM), and code that never calls the gate at all. Right now, the project's safety guarantees are "every validator we've reviewed calls the gate" — a convention enforced by one structural grep-based test. A network-level enforcement point makes it a property of the traffic, not of code discipline, and is the only design that can enforce a *combined* mutation ceiling across the Python and Java sides (today, a race-condition burst and a Java-side burst probe hitting the same target near-simultaneously could combine past either individual ceiling, and nothing currently notices).

This is worth doing before M1's live-target run reaches the point of testing real mutating techniques (API mass-assignment probing, the race-condition burst) against anything an operator cares about — those are exactly the techniques whose safety story currently rests on in-process discipline alone.

## M3 — Finish wiring Identity/Session into the Java side — **done, see `CHANGELOG_AUDIT_FOLLOWUP.md` addendum 3**

The Python/store half of this (from a prior session) is tested and works; the actual payoff — Burp's `identityCompare()` using named, persistent identities instead of an unlabeled `JOptionPane` picker — was explicitly deferred. Right now this feature is real but inert: an analyst can create identities and sessions via the API, and nothing in the tool they actually use (Burp) benefits from it. This is a comparatively contained piece of Java work (wire `identityCompare()` to query `/hosts/{host}/sessions` instead of the raw exchange pool) that converts a half-shipped feature into a used one, and it's a natural pairing with M1 since it needs a live Burp session to verify anyway.

## M4 — Cross-run finding triage and suppression — **done, see `CHANGELOG_AUDIT_FOLLOWUP.md` addendum 2**

Named in the prior session's "not started" list, and it's a real workflow gap, not a nice-to-have: without it, re-scanning the same target (which will happen constantly in real use — an analyst doesn't run this tool exactly once per engagement) re-surfaces every previously-dismissed false positive with no memory of the dismissal. For a tool whose entire value proposition is "don't make the analyst re-verify hallucinated findings," making them re-dismiss the *same* false positive on every re-run undercuts that proposition. Scope: a `suppressed` flag or fingerprint-based dedup table, keyed off the existing `fingerprint` column already in `findings` — the schema groundwork is arguably already half-there.

## M5 — Wire `risk_allocator.py`'s cost term to real data — **done, see `CHANGELOG_AUDIT_FOLLOWUP.md` addendum 2**

Small, contained, high ratio of value to effort. The formula is implemented, tested, and (per this session's audit) correctly handles the zero-cost edge case — but `cost` is never populated from `effort.EffortLedger.average_tokens` anywhere in the live path, so cost-aware ranking is fully built and never actually used. This is a few lines connecting two already-working pieces, not new design work, which makes it an efficient milestone to knock out early rather than let it sit as permanent unused infrastructure (the exact pattern `HANDOVER.md` warns about: a well-tested module that sounds complete but isn't plugged in).

## M6 — Decide, deliberately, how far to take chain-rule coverage

19 of 36 canonical categories still have no chain-detection path (now a named, tested constant — see this session's changelog). Before writing more rules reactively, this deserves an actual decision: is the goal eventual full coverage, or is chain detection meant to stay scoped to "well-documented, high-confidence escalation patterns" and accept that some categories (e.g. `anomaly`, `ai_llm` — the tool's own catch-all categories) will never have a clean pairing? Writing a rule for every remaining category to hit a number would mean inventing escalation narratives with no real security basis behind some of them, which is worse than the current honest gap. This milestone is "make the scope decision and write it down," which may or may not produce new rules as output.

## M7 — Observation as a first-class object, separate from Finding

The largest, riskiest item on this list, and rightly deferred twice already. This requires every specialist agent to change what it emits (raw observations, not just claims) — a pipeline redesign, not a bolt-on table. Whether this is worth doing depends on a real product question: does the tool's value come from agents making claims (current design) or from agents reporting evidence that a separate synthesis step reasons over (the proposed design)? That's a genuine architecture fork, not an incremental feature, and it should follow M1 — running against a real target will surface whether the current claim-based design's failure modes (agents conflating "I observed X" with "X is exploitable") are actually a practical problem worth a redesign, or a theoretical one.

## Smaller, lower-priority items (worth tracking, not worth a dedicated milestone)

- **Capability registry with input-schema validation** and **declarative rule format for `PathScorer.java`** — both explicitly scoped as "not needed yet" for a single-operator local tool per `REVIEW_INSTRUCTIONS.md`'s own settled reasoning; revisit only if the project's scope changes toward multiple operators or externally-contributed rules.
- **Persisted failed-payload history across sessions** (`payload_library.next_candidate()` currently forgets known-failing payloads between runs) — real but low-severity efficiency loss, not a correctness or safety issue.
- **Port/method-level scope granularity** on `orchestrator.py`'s host allowlist — worth doing before any scenario where "test this host" needs to mean something narrower than "test this entire host on any port."
- **`recon_validator.py`'s in-memory retention of raw header values** (this session's finding, §5 of the changelog) — **done, see `CHANGELOG_AUDIT_FOLLOWUP.md` addendum 2**.
